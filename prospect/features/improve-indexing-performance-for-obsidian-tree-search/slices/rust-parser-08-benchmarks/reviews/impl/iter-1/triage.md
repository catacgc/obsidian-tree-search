- [x] [Warning] **`bench/` directory excluded from all tsconfig.json type-checking** — While technically true (`packages/parser-native/tsconfig.json:16` includes only `"ts/**/*.ts"`), this is immaterial for a benchmark harness. The bench files are run via `bun run bench/run.ts`, and Bun's TypeScript runner will fail at execution time if types are incompatible. Furthermore, IDEs with TypeScript language servers still provide real-time type checking for these files via the workspace config. Benchmark code is not a production API surface — it's a developer tool that is executed directly and any type mismatch surfaces immediately as a runtime error during the verification step (Task 6). The risk of "hiding breaking changes in future refactors" is mitigated by the fact that the benchmark script is executed as a verification gate; if signatures change, it crashes.
- [x] [Warning] **Generated vault includes `"archive"` tag in some files' frontmatter, creating inconsistent indexing across providers** — This is a feature, not a bug. Exactly ~10% of files (those with `fileIndex % 10 === 6`) get the "archive" tag and are handled by the archive-skip path at `indexer.ts:249`. Both providers process the SAME files with the SAME `archiveTag` setting ("archive" at run.ts:63), so both skip the same files identically. The graph equivalence assertion (run.ts:200-209) verifies node AND edge counts match, meaning any divergence in archive handling between TS and WASM would be caught. Having archived files exercises a real-world code path (archive filtering) and makes the benchmark MORE thorough, not less. The concern about "masking graph divergence" is backwards — if both parsers produce the same frontmatter, they SHOULD skip the same files.
- [x] [Suggestion] **Parse-phase timing passes ALL files in one call instead of chunked** — The parse-phase benchmark deliberately measures raw parse throughput as a single batch to isolate WASM computation speed from chunking/yielding overhead. The full-indexing benchmark (lines 118-150) already uses `buildGraphFromScanner` with `chunkSize = 50`, which IS the chunked production behavior. Together, the two metrics provide complementary insights: raw parse speed (parse-phase) and realistic end-to-end behavior (full index). Adding a third "chunked parse-phase" metric would be redundant with the full-index measurement. The discrepancy is already implicitly documented by the benchmark structure.
- [x] [Suggestion] **Consider adding a check that the benchmark actually produced meaningful output** — The failure mode this guards against (both parsers equally broken producing 0 nodes) is extremely unlikely given: (1) the benchmark's graph equivalence output table (run.ts:247-258) displays actual node/edge counts visibly, so a developer would immediately notice zeros; (2) the 252 TS tests and 137 Rust tests already validate parser correctness on fixtures; (3) the `totalFilesInBatches` metric (run.ts:269) confirms 2000 files were actually processed. While a `graph.order > 0` assertion is harmless, its absence does not represent a meaningful risk — the existing assertions and visible output already surface systematic failures.
