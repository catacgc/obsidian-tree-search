### Critical (must fix before implementation)
- [ ] **Text decoration token structure contradicts TS parser behavior** — The spec (Requirement: Text Decoration Parsing, all scenarios) and tasks (Task 2 step 4 items 5-7, Task 4 tests 22-28) describe decorations as producing single tokens like `{ text: "bold content", decoration: "bold" }`. However, the actual TS `parseTokens` function produces TWO tokens for emphasis/strikethrough: `{ text: "", decoration: "bold" }` (from the `strong_open` token with empty content, confirmed at `node_modules/markdown-it/lib/rules_inline/emphasis.mjs:88`) followed by `{ text: "bold content", decoration: "none" }` (from the child `text` token). Only `code_inline` produces a single token with content. The Rust state machine described in Task 2 would produce fundamentally different output than the TS parser, causing all conformance tests (Task 6) to fail for decorated text. The implementation approach must either replicate the TS's two-token behavior or document this as an accepted divergence (contradicting AC "structurally identical output"). — `spec.md:Requirement: Text Decoration Parsing` + `tasks.md:Task 2 Step 4 items 5-7` + `tasks.md:Task 4 tests 22-28` vs `packages/core/src/parser/inline-tokens.ts:97-117`
