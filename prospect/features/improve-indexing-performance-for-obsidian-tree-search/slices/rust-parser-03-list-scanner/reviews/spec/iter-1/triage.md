### Accepted
- [ ] [Critical] **Text decoration token structure contradicts TS parser behavior** — `spec.md:Requirement: Text Decoration Parsing` + `tasks.md:Task 2 Step 4 items 5-7` + `tasks.md:Task 4 tests 22-28` vs `packages/core/src/parser/inline-tokens.ts:97-117`. Confirmed: markdown-it's emphasis `postProcess` (emphasis.mjs:88) sets `token_o.content = ''` on `strong_open`/`em_open`/`s_open`, and the TS `parseTokenList` (line 106-116) reads this empty `content` directly. For `**bold text**`, the TS produces TWO tokens: `{ text: "", decoration: "bold" }` then `{ text: "bold text", decoration: "none" }` — NOT a single `{ text: "bold text", decoration: "bold" }` as the spec and tasks describe. Only `code_inline` produces a single token with content. This means ALL spec scenarios for bold/italic/strikethrough, Task 2's state machine design (items 5-7), and Task 4 tests 22-28 specify fundamentally incorrect expected output. Conformance tests (Task 6 items 9-12) would catch this at test time but the implementation guidance is wrong.
- [ ] [Warning] **No task adds `regex` (or `regex-lite`) dependency to `Cargo.toml`** — `tasks.md:Task 2 Steps 1-2` vs `Cargo.toml` (no regex dep). Confirmed: Cargo.toml has no regex dependency, and the existing `list_scanner.rs` uses hand-written parsers. Task 2 says "Use the regex pattern..." implying regex crate usage for meta-action/meta-mdtree extraction. While hand-written parsers with capture (extending the existing `find_meta_action_end` pattern) are the better approach for WASM binary size, the task should explicitly state whether to add a regex crate or write hand-written extractors with group capture.
- [ ] [Warning] **`ImageToken.alt` conformance: TS always produces a string value, but Rust type uses `Option<String>` with `skip_serializing_if`** — `tasks.md:Task 1 (Image variant)` + `proposal.md:AC 23` vs `inline-tokens.ts:124`. Confirmed: TS line 124 uses `token.content || token.attrs?.[1]?.[1] || ""` which ALWAYS yields a string (never undefined). AC23 states "`ImageToken` (`alt`) ... are omitted from JSON when absent" but `alt` is effectively NEVER absent in the TS output. While Task 4 test 14 specifies `alt: Some("")` (correct guard), the AC wording and type definition create confusion that could lead an implementer to use `None` inappropriately, causing conformance failures.
- [ ] [Suggestion] **Task 4 test 21 description has incorrect expected text** — `tasks.md:Task 4 test 21`. Confirmed: for `"https://x.com/path) more"`, the TS URL regex `[^\s\])}>,]+` stops before `)`, so the `)` remains in subsequent text. The TS output would be `Link(href="https://x.com/path")` then `text(") more")` — including the `)` in the text token. The task says `text(" more")` which omits the paren. The conformance test (Task 6) would reveal the correct behavior, but the unit test expectation is wrong.
- [ ] [Suggestion] **Consider documenting the hand-written parser approach explicitly in Task 2** — `tasks.md:Task 2 Steps 1-2`. Given the precedent set by `list_scanner.rs` (lines 216-275, no regex crate, hand-written parsers) and the WASM binary size constraint (<2 MB compressed), Task 2 should explicitly state that meta-action/meta-mdtree extraction should use hand-written parsers with value capture (extending the existing `find_meta_action_end`/`find_meta_mdtree_end` template), not the `regex` crate.

### Dismissed
- [x] [Warning] **`LinkToken.content` conformance: TS always produces the field, but Rust type allows omission** — While the concern about `Option<String>` vs always-present is valid in principle, Task 4 tests 11-12 explicitly specify `content: Some("text")` and `content: Some("")` for all link cases, and the TS type itself declares `content?: string` (optional). The TS code at line 93 (`tokens[1]?.content`) CAN produce `undefined` in edge cases (e.g., if markdown-it doesn't generate a text token between link_open and link_close). The Rust `Option<String>` with `skip_serializing_if` correctly mirrors the optional nature of the TS type. Combined with the conformance test guard (Task 6), the implementer has sufficient guidance. This is lower risk than the `alt` case because both the TS type AND the behavior allow absence.
