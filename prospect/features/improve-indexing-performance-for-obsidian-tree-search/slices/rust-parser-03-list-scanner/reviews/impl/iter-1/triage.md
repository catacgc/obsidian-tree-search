### Accepted
- [ ] [Warning] **Empty meta-action icon produces `icon: ""` instead of absent field** — `packages/parser-native/src/inline_tokens.rs:131`. Confirmed: TS line 141 uses `icon: icon || undefined` which converts empty string to `undefined` (field absent from serialized object). Rust at line 130-132 produces `Some("")` when `(meta-action-icon::)` is present, which serializes to `"icon": ""`. This is a genuine conformance violation — the outputs are structurally different. No existing test catches this because no fixture has empty icon values, but any user with this pattern would get different behavior between parsers.
- [ ] [Warning] **Spec states bold produces "exactly TWO tokens" but implementation produces 4 (with padding)** — `spec.md:131` vs `packages/parser-native/src/inline_tokens.rs:1212`. Confirmed: Rust test `test_bold_two_tokens` expects 4 tokens (leading empty text + bold opener + content + trailing empty text) for standalone `"**bold text**"`. The conformance tests pass (comparing Rust vs TS directly), proving the implementation is correct. The spec documentation at line 131 is wrong and should be updated to say "exactly FOUR tokens" (or describe the padding behavior) to avoid misleading future maintainers.
- [ ] [Warning] **Double-backtick code spans (`` `` ``) not handled** — `packages/parser-native/src/inline_tokens.rs:521-529`. Confirmed: `find_closing_backtick` searches for any single backtick regardless of opening delimiter count. For `` ``code`` ``, Rust produces `code("") + text("code") + code("")` while markdown-it correctly produces `code("code")`. No fixture exercises this pattern, but it's a real behavioral divergence from the TS parser for users who use multi-backtick code spans. The fix is straightforward (count opening backticks and match the same count).
- [ ] [Warning] **URL inside underscore emphasis parsed differently than TS** — `packages/parser-native/src/inline_tokens.rs:407-441`. Confirmed: For `_https://example.com_`, the TS `inlineHttpLinkPlugin` regex requires `(^|\s)` before URL — this never matches inside emphasis content. But Rust's recursive `parse_inline` on inner content treats position 0 as a word boundary (`at_boundary = i == 0`), causing the URL to be parsed as a Link token inside the emphasis. This produces italic+Link in Rust vs italic+Text in TS. No fixture triggers this, but it's a genuine conformance divergence.
- [ ] [Suggestion] **Add conformance test for empty meta-action icon** — `packages/parser-native/ts/__tests__/inline-tokens.test.ts`. Directly validates the confirmed `icon: ""` vs absent bug (Warning 1). Adding this test would immediately surface the divergence.
- [ ] [Suggestion] **Add conformance test for bare bold/italic without surrounding text** — `packages/parser-native/ts/__tests__/inline-tokens.test.ts`. Current tests only use `"**important** note"` (with trailing text). Adding standalone `"**bold**"` would document the 4-token padding behavior and verify it matches TS, providing regression protection for the force-flush logic.

### Dismissed

The list scanner explicitly strips `\r` at line 359-362 (`l.strip_suffix('\r').unwrap_or(l)`) before extracting `rawText` values that are later passed to `parse_tokens`. There is no realistic scenario where `\r` reaches the inline token parser in the plugin's execution flow.
