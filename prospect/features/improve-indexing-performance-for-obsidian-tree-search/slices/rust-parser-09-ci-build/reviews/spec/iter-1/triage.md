### Dismissed
- [x] [Warning] **Task 6 incorrectly states `prebuild:wasm` is "a no-op since WASM is already built"** — While technically `wasm-pack build` does re-invoke the Cargo build system (not literally a "no-op"), with the target directory already populated from Task 3 and no source changes, Cargo performs an incremental no-work check that completes in seconds. The WASM binary is not actually recompiled. The description is imprecise but not materially confusing — an implementer will produce a correct workflow regardless of whether they understand this nuance, because the step simply runs `npm run build` which is the documented production build command. The "twice" concern is functionally irrelevant since the second invocation is effectively free.
- [x] [Suggestion] **Cargo cache key should incorporate Rust toolchain version** — While this is generally good CI practice, in this specific case the `rust-toolchain.toml` pins `channel = "stable"` and `dtolnay/rust-toolchain@stable` is used. When the stable channel increments, the new toolchain will simply recompile (a cache miss on the first run with a new version, then cached again). Cargo handles mixed-version target directories gracefully — it doesn't produce "obscure build failures" from stale incremental artifacts across minor version bumps, since it uses fingerprinting. This is a nice-to-have optimization for cache efficiency, not a correctness concern, and doesn't warrant blocking implementation.
- [x] [Suggestion] **Consider pinning wasm-pack version for reproducibility** — Valid general practice, but wasm-pack has been extremely stable (the last breaking change was years ago, 0.10→0.12 transition). The project already uses unpinned versions for many tools (Bun via `setup-bun@v2`, obsidian `latest`). The risk of a future wasm-pack breaking change is low and easily fixable if it occurs. This is not material for a 0.5-1 day slice and can be addressed reactively.
