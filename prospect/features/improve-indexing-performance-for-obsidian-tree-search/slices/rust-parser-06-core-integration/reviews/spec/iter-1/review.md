- [ ] **No error handling around `parseBatchChunk` call in batch path** — Task 3 (`tasks.md:270`) wraps each `indexSinglePage` in try/catch, but the `provider.parseBatchChunk(input)` call itself has no try/catch. If the WASM batch call panics for ANY file in a chunk (e.g., malformed content triggering an unhandled Rust edge case), all ~50 files in that chunk are lost with no indexing. The existing fallback path has per-file isolation via `indexScannedFile`'s try/catch at `builder.ts:27-47`. This is a resilience regression — on mobile (the primary target), exotic vault content could silently drop large sections of the index. — `tasks.md:270` (Task 3 batch path) vs `packages/core/src/graph/builder.ts:27-47`
- [ ] **Task 3 reads ALL `.md` file contents into memory before chunking, contradicting design's memory bound** — The feature design (step 6, iteration 3, Key Decision 7) states: "Memory is bounded to one chunk's worth of content + parsed output at a time." But Task 3's implementation (`tasks.md:250-258`) reads ALL `.md` files into `mdFiles[]` before processing any chunks: `for (const file of files) { ... mdFiles.push({ path, content, mtime }) }`. For a 2000-note vault at ~5KB/file, this holds ~10MB simultaneously. While not catastrophic, it's a stated design violation and could matter on memory-constrained mobile. The chunk-at-a-time read pattern would match the design intent. — `tasks.md:247-258` (Task 3) vs feature design Key Decision 7
- [ ] **`chunkedBatch` utility from slice 05 is built for this exact use case but goes unused** — Slice 05 implemented and tested `chunkedBatch` (`packages/parser-native/ts/index.ts:69-83`) specifically for "used by buildGraphFromScanner to avoid blocking the event loop during large vault indexing while still batching WASM calls."
