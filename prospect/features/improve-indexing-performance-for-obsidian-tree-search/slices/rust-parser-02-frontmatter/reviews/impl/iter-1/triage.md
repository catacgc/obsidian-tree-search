### Accepted
- [ ] [Critical] **`find_body_start_line` produces incorrect result for CRLF content with non-zero `frontmatter_body_start`** — `packages/parser-native/src/list_scanner.rs:468-481`. Confirmed by trace: for CRLF content `"---\r\ntitle: Hello\r\n---\r\n- [[Note]]"`, both TS and Rust frontmatter parsers produce `bodyStart=22`. But after CRLF stripping at line 354-357, the lines lose their `\r` chars while `bodyStart` still includes them. The accumulator `line.len() + 1` only accounts for `\n` (not `\r\n`), so it never reaches 22 (gets to 21 for 3 frontmatter lines). Rust returns `lines.len()` (line 481) → scans nothing → empty results. TS survives because its default `bodyStartLine = 0` means it scans from the start, where frontmatter lines harmlessly don't match patterns.

Confirmed: the CRLF test (line 99) uses `bodyStart=0`, and the frontmatter test (line 115) uses LF content. No test combines both. Adding this test would immediately catch the Critical bug above.
- [ ] [Warning] **`find_body_start_line` fallback behavior diverges from TS** — `packages/parser-native/src/list_scanner.rs:481`. When the loop exhausts all lines without finding the target offset, Rust returns `lines.len()` (scan nothing) while TS remains at `bodyStartLine = 0` (scan everything). Even after fixing the CRLF counting, the fallback should return 0 (matching TS) for robustness against any future edge case where the character count doesn't align.

- [x] [Suggestion] **Unicode tag characters diverge between TS and Rust** — The reviewer claims JS `\w` "matches Unicode letters (depending on engine flags)" but this is factually incorrect. The regex `/#([\w/]+)/g` at `list-scanner.ts:7` has NO `u` flag. In JavaScript, `\w` without the `u` flag is always `[A-Za-z0-9_]` (ASCII only) across all engines (V8, JSC, SpiderMonkey). The Rust `is_tag_char` at line 211-213 checks `is_ascii_alphanumeric() || '_' || '/'` — which is equivalent. There is no divergence between TS and Rust for tag character matching.
