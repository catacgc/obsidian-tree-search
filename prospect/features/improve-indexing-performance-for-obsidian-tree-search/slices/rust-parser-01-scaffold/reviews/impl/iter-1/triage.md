### Dismissed
- [x] [Suggestion] **Spec scenario "Empty frontmatter block" uses incorrect input/output** — While factually correct (the spec says `"---\n---\nbody"` → bodyStart=7, but both parsers return bodyStart=0 for that input), this is immaterial for implementation. The Rust implementation and tests correctly use `"---\n\n---\nbody"` which is the valid test case. The spec document is a reference, not executable code — the implementation is correct and tests pass. This is documentation errata that doesn't affect correctness or risk of the delivered code.
- [x] [Suggestion] **Loader test for invalid bytes doesn't test `loadNativeParser` directly** — The test comment explains that wasm-pack glue caches module state globally, making it impossible to test rejection after a successful load in the same process. Testing `WebAssembly.instantiate` directly verifies the underlying mechanism. The actual `loadNativeParser` path is exercised successfully in the preceding tests (lines 9-21). The error propagation path is trivial (async exception bubbles up). This is a pragmatic testing limitation, not a risk.
- [x] [Suggestion] **Duplicate type definitions: `WasmExports` and `NativeParserHandle` are identical** — While technically redundant today, these types serve different conceptual purposes: `WasmExports` is the internal loader return type (implementation detail), `NativeParserHandle` is the public consumer-facing API type. As future slices add WASM exports (e.g., `batch_parse_chunk`, `parse_tokens`), the `NativeParserHandle` type will be the one that consumers depend on and `WasmExports` will be the raw internal contract. The duplication is intentional separation of concerns and will diverge naturally. No risk of divergence causing bugs since both are updated in the same package.
