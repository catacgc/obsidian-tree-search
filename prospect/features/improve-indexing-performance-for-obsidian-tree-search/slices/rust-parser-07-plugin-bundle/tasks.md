## Task 2 — Create esbuild WASM inline plugin in `esbuild.config.mjs`

**Action:** Add a custom esbuild plugin named `wasmInlinePlugin` to `esbuild.config.mjs`. The plugin:
1. Uses the `onResolve` hook with `filter: /\.wasm$/` to intercept `.wasm` imports. When matched, returns `{ path: resolvedAbsolutePath, namespace: 'wasm-inline' }`.
2. Uses the `onLoad` hook for the `wasm-inline` namespace to: read the `.wasm` file from disk with `fs.readFileSync`, convert to base64 via `Buffer.from(bytes).toString('base64')`, and return a JS module that exports the base64 string as default: `{ contents: 'export default "' + base64 + '"', loader: 'js' }`.

Additionally, add a `loader` entry to `esbuildOptions` to suppress esbuild's static asset handling of the `new URL('parser_native_bg.wasm', import.meta.url)` pattern found at `packages/parser-native/pkg/parser_native.js:341`:
```javascript
loader: { '.wasm': 'empty' },
```
This prevents esbuild from copying `parser_native_bg.wasm` to `dist/` as a file asset. The `onResolve`/`onLoad` plugin hooks take priority over the `loader` for explicit `.wasm` imports, so the base64 inlining still works for the explicit import in `src/wasm/parser-native-wasm.ts`.

Register `wasmInlinePlugin` in the `plugins` array before the existing plugins.

**Why:** The `loader: { '.wasm': 'empty' }` is necessary because the wasm-pack generated glue code contains `new URL('parser_native_bg.wasm', import.meta.url)` which esbuild's default `.wasm` loader (`file`) would process as an asset reference, emitting `parser_native_bg.wasm` to `dist/`. While this code path is unreachable at runtime (since `loadWasm` always passes bytes explicitly), esbuild processes it statically at build time.

**Verification:** `node esbuild.config.mjs production` builds without error. `dist/main.js` contains a long base64 string. No `.wasm` file exists in `dist/`. All existing features (CSS, manifest copy, externals) still work.

## Task 3 — Create WASM bytes module (`src/wasm/parser-native-wasm.ts`)

**Action:** Create `src/wasm/parser-native-wasm.ts` with:
```typescript
// @ts-ignore — esbuild resolves this to a base64 string module via wasmInlinePlugin
import wasmBase64 from "../../packages/parser-native/pkg/parser_native_bg.wasm"

function decodeBase64(base64: string): Uint8Array {
  const binaryString = atob(base64)
  const bytes = new Uint8Array(binaryString.length)
  for (let i = 0; i < binaryString.length; i++) {
    bytes[i] = binaryString.charCodeAt(i)
  }
  return bytes
}

export const wasmBytes: Uint8Array = decodeBase64(wasmBase64)
```

Note: The import path `../../packages/parser-native/pkg/parser_native_bg.wasm` is resolved by the esbuild `wasmInlinePlugin` `onResolve` hook (which intercepts any path ending in `.wasm`). At runtime, `wasmBase64` is the inlined base64 string.

**Verification:** TypeScript compilation passes (the `@ts-ignore` handles the `.wasm` import). The module exports a `Uint8Array`. The esbuild build includes this module correctly.

## Task 4 — Create native parser loader (`src/indexing/load-native-parser.ts`)

**Action:** Create `src/indexing/load-native-parser.ts` exporting:
```typescript
import type { ParserProvider } from "@mdtree/core"

export async function loadNativeParserProvider(): Promise<ParserProvider | null> {
  try {
    const { wasmBytes } = await import("../wasm/parser-native-wasm")
    const { loadNativeParser, createNativeParserProvider } = await import("@mdtree/parser-native")
    const handle = await loadNativeParser(wasmBytes)
    return createNativeParserProvider(handle)
  } catch (error) {
    console.warn("[mdtree] Failed to load native WASM parser, falling back to TypeScript parser:", error)
    return null
  }
}
```

The dynamic `import()` calls are used so that if the WASM bytes module or parser-native module fails to load (e.g., missing WASM binary, incompatible environment), the error is caught in the try/catch. With `bundle: true` in esbuild, these dynamic imports are bundled inline (not separate chunks), so no filesystem access is needed at runtime.

**Verification:** The function type-checks. When WASM is available, returns a `ParserProvider`. When WASM loading fails (e.g., in test environment without WASM), returns `null` gracefully.

## Task 5 — Modify `IndexedTree` to accept optional `ParserProvider` via setter

**Action:** Edit `src/indexing/indexed-tree.ts`:
1. Add import: `import type { ParserProvider } from "@mdtree/core"`.
2. Add a private field: `private provider: ParserProvider | undefined`.
3. Add a public setter method:
   ```typescript
   setParserProvider(provider: ParserProvider): void {
     this.provider = provider
   }
   ```
4. In `refresh()`, pass `this.provider` as the third argument to `buildGraphFromScanner`:
   ```typescript
   const graph = await buildGraphFromScanner(
     new ObsidianVaultScanner(this.vault, this.metadataCache),
     { parentRelation: settings.parentRelation, archiveTag: settings.archiveTag, searchSeparator: settings.searchSeparator },
     this.provider,
   )
   ```
5. In `refreshPage()`, pass `this.provider` as the fifth argument to `reindexFileInGraph`:
   ```typescript
   await reindexFileInGraph(
     file.path,
     this.graph,
     new ObsidianVaultScanner(this.vault, this.metadataCache),
     { parentRelation: settings.parentRelation, archiveTag: settings.archiveTag, searchSeparator: settings.searchSeparator },
     this.provider,
   )
   ```

**Rationale for setter over constructor:** The feature design says "Constructor accepts `ParserProvider`", but this is architecturally incorrect for the actual code flow. `IndexedTree` is constructed at `main.ts:43` synchronously, but WASM loading is async (it must `await` WebAssembly.instantiate). A setter allows setting the provider after async loading completes but before the first `refresh()`. The design intent (thread provider to core) is fully satisfied.

**Verification:** Type-checks. When no provider is set (`undefined`), `buildGraphFromScanner` and `reindexFileInGraph` receive `undefined` and operate in fallback mode (unchanged behavior). When a provider is set, it's threaded through.
