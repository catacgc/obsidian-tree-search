### Accepted
- [ ] [Critical] **`parseTokens` in `text-lines.ts` (canvas path) is not covered by the `DvList.parsedTokens` optimization** — `packages/core/src/parser/text-lines.ts:82` + design Integration Points. Confirmed: `buildNodesFromTextLines` → `createTextNode` → `parseTokens(text)` operates on `NodeTextLine` objects from canvas parsing, not `DvList` items. The `ParserProvider` injection path (`buildGraphFromScanner` → `parseVaultFile`) never reaches `parseCanvasData` → `buildNodesFromTextLines`. The design must expose a standalone `parseTokens` function on `ParserProvider` or explicitly acknowledge this path remains on the TS parser.
- [ ] [Critical] **`parseTokens` call at `indexer.ts:238` for frontmatter parent fields is unaddressed** — `packages/core/src/graph/indexer.ts:238`. Confirmed: `parseTokens(parent)` is called on raw frontmatter strings inside `indexSinglePage`, which does NOT receive a `ParserProvider` and these strings are not `DvList` items. While the performance impact is negligible (short strings, at most N calls), the design explicitly discusses all `parseTokens` call sites and proposes a solution (`DvList.parsedTokens`) that structurally cannot cover this one. The `ParserProvider` must expose a standalone `parseTokens(text)` method for design completeness.
- [ ] [Warning] **Batch API memory pressure on mobile not addressed** — `packages/core/src/graph/builder.ts:68-75` + design Integration Points. Confirmed: the current code processes files one-at-a-time with yielding. The design states "collects file contents and calls batch API before indexing" without specifying chunking. For 2000 files (~10-20 MB content), holding all content plus all JSON-serialized parsed results simultaneously doubles peak memory on mobile devices with constrained resources.
- [ ] [Warning] **Batch WASM call blocks event loop, conflicting with existing yielding pattern** — `packages/core/src/graph/builder.ts:69-70`. Confirmed: the current code yields every 10 files via `setTimeout(0)`. A single synchronous WASM call processing 2000 files cannot yield mid-execution. On mobile (the primary motivation), this risks UI freezes — the very problem the feature aims to solve.
- [ ] [Warning] **Slice 06 proposal description contradicts design's injection approach** — `openspec/changes/rust-parser/proposal.md:60` says "conditional import in `vault-file.ts` and `inline-tokens.ts`" while design Key Decision 3 says "No dynamic `import()` in core — the provider is set externally by the consumer." These are mutually exclusive approaches that could confuse implementers.
- [ ] [Warning] **Custom frontmatter parser risks breaking full YAML support** — `packages/core/src/parser/frontmatter.ts` returns full `Record<string, unknown>`; `indexer.ts:235` reads `page.file.frontmatter[settings.parentRelation]` where `parentRelation` is user-configurable. The batch API signature (`path, content, mtime, archiveTag`) doesn't pass `parentRelation`, so the Rust parser either can't know which field to extract, or must parse ALL frontmatter keys. The "lightweight" approach needs to at minimum emit all key-value pairs it can parse, not just three hardcoded fields.
- [ ] [Warning] **`parseCanvasData` not listed as an integration point** — `packages/core/src/graph/builder.ts:40` calls `parseCanvasData` which internally calls `buildNodesFromTextLines` → `parseTokens`. The design's Integration Points table omits this entirely, leaving no defined mechanism for the canvas path to use the native parser.
- [ ] [Suggestion] **Consider explicit chunked batching specification** — design Integration Points. Specifying chunk size (e.g., 50-100 files per WASM call) would bound memory usage, allow event-loop yielding between chunks, and preserve the existing responsive behavior on mobile.
- [ ] [Suggestion] **`wasm-pack --target web` ES module output may need esbuild handling** — `esbuild.config.mjs:54` uses `format: "cjs"`. While esbuild can bundle ES imports into CJS, the `--target web` glue code typically uses `fetch()` for `.wasm` loading, which conflicts with the base64-inline strategy. Slice 07 should explicitly document how the glue code is adapted or bypassed.

### Dismissed
- [x] [Warning] **Proposal constraints section says "consider direct memory access or MessagePack" but design decides JSON** — The proposal (line 70) uses the word "consider" — it's a suggestion to evaluate options, not a mandate. The design DID consider alternatives and chose JSON with explicit reasoning (Key Decision 1). The constraint is satisfied. This is a resolved suggestion, not a contradiction.
- [x] [Suggestion] **CI workflow uses `npm install`; project uses Bun workspaces** — The existing `.github/workflows/main.yml` is a tag-triggered release workflow that builds and publishes the plugin. Slice 09 would add a *new* CI workflow for WASM builds and testing, not modify the release workflow. The existing workflow's use of `npm install` is a pre-existing debt unrelated to this feature's design specification.
