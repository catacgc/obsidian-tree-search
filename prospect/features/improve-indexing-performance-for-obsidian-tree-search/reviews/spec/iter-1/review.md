### Warnings
- [ ] **Batch API memory pressure on mobile not addressed** — The design states `buildGraphFromScanner` "collects file contents and calls batch API before indexing." For a 2000-file vault, this means holding all file contents (potentially hundreds of MB) + all parsed results simultaneously in memory. The current architecture processes one file at a time with yielding (`BATCH_SIZE = 10`). On mobile devices with constrained memory, this could cause OOM. No chunked batching strategy is specified. — `prospect/features/.../design.md:Integration Points` + `packages/core/src/graph/builder.ts:68-75`
- [ ] **Batch WASM call blocks event loop, conflicting with existing yielding pattern** — `builder.ts` yields to the event loop every 10 files via `setTimeout(0)`. A single WASM batch call processing 2000 files is synchronous and cannot yield. This could cause UI freezes on mobile (the original motivation). The design should specify batch chunk sizes or an async iteration strategy. — `packages/core/src/graph/builder.ts:69-70` + `prospect/features/.../design.md:Key Decision 4`
- [ ] **Slice 06 proposal description contradicts design's injection approach** — The proposal says slice 06 will add "conditional import in `vault-file.ts` and `inline-tokens.ts`" but the design explicitly states "No dynamic `import()` in core — the provider is set externally by the consumer." These are contradictory approaches. The slice description should align with the design's strategy pattern. — `openspec/changes/rust-parser/proposal.md:60` vs `prospect/features/.../design.md:Key Decision 3`
- [ ] **Proposal constraints section says "consider direct memory access or MessagePack" but design decides JSON** — The `openspec/changes/rust-parser/proposal.md` Constraints section says serialization "must be efficient (consider direct memory access or MessagePack)" while the design explicitly chooses JSON. This internal contradiction should be resolved in the proposal to match the design decision. — `openspec/changes/rust-parser/proposal.md:70` vs `prospect/features/.../design.md:Key Decision 1`
- [ ] **Custom frontmatter parser risks breaking full YAML support** — The design chooses a lightweight custom Rust parser for frontmatter that only handles `aliases`, `tags`, and parent fields. But `parseFrontmatter` currently returns the FULL `Record<string, unknown>` frontmatter, and `indexSinglePage:207` reads `page.file.frontmatter["tags"]` as an array. Users could have arbitrary frontmatter keys consumed via the `parentRelation` setting (user-configurable field name). The Rust parser must handle ALL YAML structures the user might put in frontmatter, not just three hardcoded fields. — `packages/core/src/parser/frontmatter.ts:11-27` + `prospect/features/.../design.md:Key Decision 6`
- [ ] **`parseCanvasData` not listed as an integration point** — Canvas files use `parseCanvasData` which internally calls `buildNodesFromTextLines` → `parseTokens`. The design's integration point table omits this entirely. Canvas indexing represents a separate code path from markdown file parsing that also needs native parser injection. — `prospect/features/.../design.md:Integration Points` + `packages/core/src/graph/builder.ts:33-35`

### Suggestions
- [ ] **Consider explicit chunked batching specification** — Instead of "collects file contents and calls batch API," specify chunk size (e.g., 50-100 files per WASM call) to bound memory usage and allow event-loop yielding between chunks. This preserves the current responsive behavior. — `prospect/features/.../design.md:Integration Points`
- [ ] **CI workflow uses `npm install`; project uses Bun workspaces** — The existing `.github/workflows/main.yml` uses `npm install` and Node.js, but the project uses Bun workspaces (`package.json` workspaces) and `bun test`. Slice 09 (CI build) should account for this discrepancy — the existing CI may need updating. — `.github/workflows/main.yml:27-28`

While esbuild can bundle ES imports into CJS output, this interaction should be explicitly tested in slice 07. — `esbuild.config.mjs:53` + `prospect/features/.../design.md:Key Decision 8`
